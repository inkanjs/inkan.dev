I write inkan, so take this page with that in mind. I have tried to put down where each of
the others is the better choice, because for a lot of projects one of them is. If
something here is wrong or out of date, [open an issue](https://github.com/inkanjs/inkan/issues)
and I will fix the page.

## Express

Express is the one everybody knows. Almost every Node tutorial uses it, most people you hire
have shipped it, and for nearly any problem there is a middleware that someone has kept
alive for years. The API is small: a request, a response, `next()`. Express 5 finally hands
a rejected promise from an async handler to the error middleware, so the oldest trap is gone.

What it leaves to you is everything about the shape of the data. Validation, the types of
`req.body`, an OpenAPI document and the docs are separate tools (zod or express-validator,
swagger-jsdoc or a hand-written spec), and nothing makes them agree with the handler. It is
also the slowest of Express, Fastify, Hono and inkan by a wide margin on the bench below, mostly in routing: with 400
routes or a 404 it does about a fifth of what bare `node:http` does.

**Pick Express when** the team knows it well, you depend on middleware that only exists for
Express (a Passport strategy, an SDK that ships an Express adapter), and request throughput
is not what limits you.

## Fastify

Fastify is the mature fast one. It has run in production for years, in a lot of places, its
plugin system with encapsulation is well thought out, and
the `@fastify/*` packages cover most of what an API needs. Routes carry JSON Schema, which it
compiles with Ajv for the input and with fast-json-stringify for the output, so answers are
trimmed to their schema. Pino logging is built in, and a type provider (TypeBox or Zod) gives
the handler its types.

The costs are in the wiring. OpenAPI and a docs page come from `@fastify/swagger` and
`@fastify/swagger-ui`; tests are yours to write. The validators are compiled at runtime with
`new Function`, which only matters if you run somewhere that forbids it (a strict CSP, some
sandboxes). On the bench it is level with inkan: ahead on params and query, behind on large
answers and on 400s.

**Pick Fastify when** you want a proven framework with a large plugin catalogue and JSON
Schema as your contract language, and you are fine assembling docs and contract tests from
separate parts.

## Hono

Hono is built on web standards: a `Request` in, a `Response` out. That is why it runs nearly
everywhere unchanged: Cloudflare Workers, Deno, Bun, Vercel and Netlify edge functions, AWS
Lambda, and Node through `@hono/node-server`. It is small, starts fast, and its RPC client
(`hc`) types calls from the server's routes. Validation is a middleware (`@hono/zod-validator`
and friends), and `@hono/zod-openapi` writes an OpenAPI document from Zod schemas.

The bench below only measures Node, where Hono runs through an adapter. On Bun or Workers it
is at home, and these numbers say nothing about that.

**Pick Hono when** your API runs at the edge or on Workers, or cold start and bundle size
matter more to you than anything on this page.

## Koa

Koa is Express done again by the same people, around `async`/`await`: one context object
instead of a request and a response, and middleware that wraps the rest of the chain, so it
can act both before and after the handler. The core is tiny and leaves almost everything to
packages: routing (`@koa/router`), body parsing, validation. Code written for it tends to be
clean and easy to follow.

On the bench below it comes last, and that needs a word. `@koa/router` tests each request
against every route, and the bench app has 800 of them. With two routes Koa is level with
Express. So the number is fair for a big Koa app on the standard router, not for Koa itself.

**Pick Koa when** you like the onion model of middleware, your app has tens of routes rather
than hundreds, and you want to choose every piece yourself.

## hapi

hapi is built for large teams and long-lived services. Routes are configuration objects
with validation (Joi), auth strategies, caching and lifecycle extensions next to the handler,
and plugins have explicit dependencies and their own config. It came out of Walmart, where it
carried Black Friday traffic, and it puts a lot of care into security defaults.

It is more ceremony than the others for a small API, and its ecosystem is mostly its own
(`@hapi/*`) rather than the wider middleware world. On the bench it is a little ahead of
Express overall, and clearly ahead on routing.

**Pick hapi when** a large team needs strong conventions, auth and validation configured per
route, and you value stable, careful releases over speed.

## h3

h3 is the server under Nitro and Nuxt. Like Hono it is built on web-standard requests and
responses and runs on Node, Bun, Deno, Workers and more, with small composable helpers
(`readBody`, `getQuery`) instead of a big framework object. On the bench it is the fastest of
the newcomers and not far behind Hono, strong on large bodies and answers.

**Pick h3 when** you are in the Nuxt or Nitro world, or want a small, standards-based server
that runs on several runtimes, and you bring your own validation and docs.

## Elysia

Elysia is made for Bun, and its idea is close to inkan's: a schema per route (TypeBox) gives
validation, the handler's types, an OpenAPI document and an end-to-end typed client (Eden).
It is fast and pleasant to write, and on Bun it is among the fastest servers in JavaScript.

On Node it runs through `@elysiajs/node`, and the bench only measures that. It does well on
answers without input, and loses about half wherever its schemas read params or a body,
because each request first goes through the adapter. Measure it on Bun before you judge it.

**Pick Elysia when** you run on Bun and want contracts, types and a typed client from one
place. On Node, inkan or Fastify give you the same idea for less.

## NestJS

NestJS is a full application framework: modules, dependency injection, decorators,
guards, pipes and interceptors, in the style of Angular or Spring. It brings an answer for
almost everything (OpenAPI, GraphQL, queues, microservices, testing) and a structure that
many developers already know, which is a lot when a big team builds a big app.

It sits on Express or Fastify and adds its own layer, so it is never faster than the one
beneath it. On its default Express platform it lands a little below Express on the bench.
Validation is usually `class-validator`, which the bench does not use; there it checks by hand.

**Pick NestJS when** the app is large, the team wants one structure and DI everywhere, and
the speed of a single request matters less than how the codebase holds together.

## inkan

inkan starts from one contract per route: params, query, headers, body, the answers per
status, and a few examples. From that it validates the input, types the handler, checks the
answer in development and trims it to the schema, writes OpenAPI 3.1, serves a docs page, and
runs every example as a test with `inkan check`. `inkan diff` compares the contract with the
one you shipped last and names what would break a client. It has no runtime dependencies and
no `eval`, and runs on `node:http`, with `app.fetch` for Bun, Deno and serverless.

What speaks against it: it is young. 0.8 is the first release with a frozen API, it has one
maintainer, and the plugin catalogue on [Hanko](/hanko) is small next to Express or Fastify.
If you need an integration nobody has written, you will be the one writing it. It is also
Node first: `app.fetch` works on other runtimes, but I test and measure on Node.

**Pick inkan when** other people or teams call your API and you want its docs and its
contract held to the code in CI, you are starting on Node, and a young project with a small
ecosystem is a risk you can take.

If you have an app on one of the others, [from Express](/docs/migrate/express) and
[from Fastify](/docs/migrate/fastify) go through it part by part, with both versions next to
each other, and show how to move one route at a time instead of all at once.
