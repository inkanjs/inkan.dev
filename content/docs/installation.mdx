---
title: "Installation"
description: "Install inkan, start an app, try the example."
---

```sh
npm install @vxnsin/inkan
```

The package is scoped because npm keeps the plain name `inkan` free of look-alikes. The command it installs is `inkan` either way.

Node 22 or newer. On Node 22.18 and newer, `.ts` files run as they are,
with no build step and no loader.

## Start a project

```sh
npm create inkan@latest my-api
```

It asks three things: where the data lives, whether you want logins, and whether a frontend
goes next to the API. Then it writes the project into `my-api` and installs it. Flags answer
the questions before they are asked (with npm, they go after `--`):

```sh
npm create inkan@latest my-api -- --store postgres --auth --frontend vite
```

| option | |
| --- | --- |
| `--store memory\|postgres\|redis\|mongo\|mysql` | where the data lives. `memory` (the default) needs nothing; the others go through `@inkanjs/postgres`, `redis`, `mongo` or `mysql` |
| `--auth`, `--no-auth` | logins and sessions from `@inkanjs/auth` (default: none) |
| `--frontend none\|next\|vite` | a Next.js or Vite frontend, with the API under `/api` through `@inkanjs/next` or `@inkanjs/vite` (default: none) |
| `--pm npm\|pnpm\|yarn\|bun` | who installs, and what the CI workflow uses. By default the one that ran the command |
| `--no-install` | write the files, install nothing |
| `--yes`, `-y` | ask nothing: the defaults for whatever the flags leave open |
| `--force` | write into a folder that is not empty |

Without a terminal to ask in, it takes the defaults as well, so it works in a script.
`npm create inkan` runs `inkan create app` of the inkan with the same version; with inkan
installed, `npx inkan create app my-api` does the same.

What you get:

- `src/app.ts` builds the app and exports it, without listening: a health route and a small
  notes API, each with its contract and its examples.
- `src/store.ts` is where the data lives. Swap the store there and nothing else changes.
- `src/server.ts` is the one file that opens a port. With Next.js there is none: `next start`
  serves the API through `app/api/[...path]/route.ts`.
- `test/` runs every example as a test (`app.check` with `strict`) and the cases examples
  are not for (`app.inject`).
- `.github/workflows/ci.yml` starts the database, if there is one, and runs the typecheck,
  `inkan check --strict` and the tests, with the same package manager.
- `.env.example` with what the store needs, and a README that says what is where and what to
  change first.

With a frontend, the API's files move out of its way: to `server/` with Next.js, to
`src/server/` with Vite. Every combination passes `inkan check --strict` and its own tests as
it comes. With `--auth`, the app exports an [`untested`](/docs/examples#untested) for the few
statuses the auth plugin promises that no single example can show.

<Callout type="warn" title="Experimental">
  The generated files may change in any release.
</Callout>



## Try the example


```sh
npx @vxnsin/inkan examples         # pick one, and it lands in a folder of its own
```

Six example projects, in reading order, each explained file by file:

| | |
| --- | --- |
| `hello` | one route, one example, `inkan check`. Five minutes. |
| `tea-shop` | CRUD with named schemas, `problem()`, groups and `beforeEach` |
| `auth` | middleware, `ctx.state`, route-level `use`, a 401 and a 403 in the contract |
| `testing` | `app.check()` and `app.inject()` in `node:test`, plus a CI workflow |
| `openapi` | export the document, generate a client, keep both in sync |
| `deploy` | Dockerfile, `$PORT`, JSON logs, graceful shutdown, warden |

Every one has a README that says what to read in which order, something to change first,
and a list of ways to break it on purpose to see what inkan catches.

Or the one in this repo:

```sh
git clone https://github.com/inkanjs/inkan && cd inkan && npm install
node examples/shop.ts              # then open http://localhost:3000/docs
node src/cli.ts check examples/shop.ts
```
