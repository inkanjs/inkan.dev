---
title: "Examples are tests"
description: "Examples show up in the docs and run as tests."
---

```sh
npx inkan check src/app.ts            # every route
npx inkan check src/app.ts --only /teas
npx inkan check src/app.ts --json     # for CI
npx inkan check src/app.ts --format markdown   # for a pull request comment
npx inkan check src/app.ts --strict   # a promised status without an example fails too
```

A route that promises a 404 no example ever shows is listed under the route,
and on the docs page. Nothing tests that 404 yet; `--strict` turns it into a
failure, unless the route says it is [untested on purpose](#untested).

The entry file exports the app (`export default app` or `export const app`).
`app.listen()` stays quiet while the CLI loads it. If the examples change data,
export a `beforeEach` that puts it back. It runs before every example:

```ts
export function beforeEach() {
  store.reset();
}
```

Or inside your own tests:

```ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { app, beforeEach } from "./app.ts";

test("the contract holds", async () => {
  const report = await app.check({ beforeEach });
  assert.equal(report.failed, 0);
});
```

## untested

Some statuses no example can show: a 429 after many failed logins, a 503 when the database
is down. A route says so, with the reason, and `--strict` lets them be:

```ts
app.post(
  "/login",
  {
    body: Login,
    response: { 200: Session, 401: t.problem(), 429: t.problem() },
    examples: [
      { name: "signed in", body: { name: "ana", password: "tea" } },
      { name: "wrong password", body: { name: "ana", password: "coffee" }, status: 401 },
    ],
    untested: { 429: "a lockout takes many failed logins" },
  },
  login,
);
```

`inkan check --strict` lists the 429 under the route with its reason, as "not demonstrated,
on purpose", and does not fail on it. An example that does answer with it still counts. The
report has them in `untested`, each `{ method, path, status, reason }`.

Routes the app does not write itself, a plugin's, take the same from the entry. The CLI reads
`export const untested` as it reads `beforeEach`, keyed by `METHOD /path`:

```ts
export const untested = {
  "POST /auth/login": { 429: "a lockout after many failed logins" },
  "POST /auth/logout": { 403: "a logout from another site" },
};
```

In your own tests, hand it to `app.check()`:

```ts
const report = await app.check({ beforeEach, untested, strict: true });
```

`untested` is experimental.

## Examples that build on each other

"Create a tea, then fetch it" needs the id from the first answer. One example `keep`s it,
the next one runs `after` it and uses it as a placeholder:

```ts
// POST /teas
{ name: "a new oolong", body: { name: "Da Hong Pao", kind: "oolong" }, keep: { id: "body.id" } },

// GET /teas/:id
{ name: "the one just added", after: "POST /teas > a new oolong", params: { id: "{id}" }, expect: { name: "Da Hong Pao" } },
```

`keep` reads `body.…`, `headers.…`, `cookies.…` (a cookie the answer sets) or `status`. A
placeholder alone (`"{id}"`) keeps the value's type; inside text (`"/teas/{id}"`) it
becomes text. `beforeEach` runs once before the whole chain, so the examples in it see each
other's data, and the order comes from `after`, never from the order of the files. The docs
page runs the chain too when you press send.

### Cookies

The examples of one chain share a cookie jar, as a browser would. A cookie an answer sets
goes with the requests after it that its `Path` covers, until an answer clears it
(`Max-Age=0`, or an `Expires` gone by). So a login and a `/me` after it pass without
copying the session by hand:

```ts
// POST /login
{ name: "ana signs in", body: { name: "ana", password: "tea" }, keep: { sid: "cookies.sid" } },

// GET /me
{ name: "who she is", after: "POST /login > ana signs in", expect: { name: "ana" } },
```

Every chain starts with an empty jar, so nothing crosses into another chain. `keep` with
`cookies.<name>` is for when you need the value itself, in a header or a body.

For everything the examples do not cover, `app.inject()` sends a request
straight in, without a socket:

```ts
const res = await app.inject({ method: "POST", url: "/teas", body: { name: "Gyokuro" } });
res.status; // 400
res.body.errors; // [{ in: "body", path: "kind", message: "is required" }, …]
```
