A plugin is worth more once other people can find it. This page is about the step after
[Writing a plugin](/docs/plugins): putting it on npm so it works with every inkan app, and
listing it on [Hanko](/hanko), next to the official ones.

<Callout title="Coming with 0.7.0">
  `npx @vxnsin/inkan create plugin` and the `inkan` option of `plugin()` are new in inkan 0.7.0.
</Callout>

## Start from the template

```sh
npx @vxnsin/inkan create plugin tenant
```

Makes a folder with a shared plugin, a test that runs it through `app.inject`, a README to
fill in, and a `package.json` that already has the name, the keyword and the peer dependency
this page asks for. Everything below is what the template does for you, and why.

## Naming

| name | for |
| --- | --- |
| `inkan-<name>` | community plugins: `inkan-tenant`, `inkan-prometheus` |
| `@you/inkan-<name>` | the same under your own scope, if you keep one |
| `@inkanjs/*` | reserved for the official packages |

Name it after what it does, not after inkan: `inkan-tenant`, not `inkan-plugin-tenant`.

## package.json

```json
{
  "name": "inkan-tenant",
  "keywords": ["inkan", "inkan-plugin"],
  "type": "module",
  "peerDependencies": {
    "@vxnsin/inkan": ">=0.7.0"
  }
}
```

- **The keyword `inkan-plugin`** is how a plugin is found on npm, Hanko or not.
- **inkan is a peer dependency**, never a dependency. The app brings its own inkan; a second
  copy in your package would give it a second `t`, a second `problem` and types that do not
  line up. Put the oldest version you test against in the range.

## Say which inkan it works with

npm only warns about a peer dependency that does not fit. The plugin can say it too, as a
range in its options, and inkan checks it when the plugin is registered:

```ts
import { plugin } from "@vxnsin/inkan";

export const tenant = (o: { header: string }) =>
  plugin((app) => app.decorateRequest("tenant", (ctx) => ctx.rawHeaders[o.header]), {
    shared: true,
    name: "inkan-tenant",
    inkan: ">=0.7.0 <0.8.0",
  });
```

Keep the range the same as the peer dependency's.

## What makes a good one

- **Zero or few dependencies.** inkan has none, and the official middleware runs on
  `node:crypto` alone. Every dependency you add is one every app installs.
- **Typed through the app.** Make it a shared plugin that returns its scope, so `ctx.user` or
  `ctx.tenant` is typed after `register` with no generics to write. See
  [typed decorations](/docs/plugins#typed-decorations-out-of-shared-plugins).
- **Honest in the OpenAPI document.** A plugin that adds a header, an answer or a security
  scheme says so with [`describe()`](/docs/plugins#describe-adding-to-openapi). Then `/docs`
  shows the 401 your plugin can send.
- **Tested with `app.inject`.** No port, no network: build a small app, register the plugin,
  inject requests.

  ```ts
  import { test } from "node:test";
  import assert from "node:assert/strict";
  import { inkan } from "@vxnsin/inkan";
  import { tenant } from "./index.ts";

  test("reads the tenant from the header", async () => {
    const app = inkan().register(tenant({ header: "x-tenant" })).get("/", (ctx) => ({ tenant: ctx.tenant }));
    const res = await app.inject({ method: "GET", url: "/", headers: { "x-tenant": "tea" } });
    assert.deepEqual(res.body, { tenant: "tea" });
  });
  ```

- **A README with three parts:** how to install it, the smallest example that does something,
  and every option with its default. That README is what Hanko links to.

## Getting listed on Hanko

The keyword is enough. Hanko asks npm once a day for every package with the keyword
`inkan-plugin` and lists it under community, with its version, its last publish and last
week's downloads. No form, no pull request.

A pull request to [inkanjs/inkan.dev](https://github.com/inkanjs/inkan.dev) is only for
more than npm knows: a better line than the package description, tags to be found by, or a
link to docs of your own. Add an entry to the `community` part of `data/hanko.ts`; it takes
the place of what npm says:

```ts notwoslash
{
  name: "inkan-tenant",
  description: "One line: what it does, not how good it is.",
  kind: "community",
  href: "https://github.com/you/inkan-tenant#readme", // the README, docs, or the npm page
  npm: "inkan-tenant",
  repo: "https://github.com/you/inkan-tenant",
  tags: ["multi-tenant", "headers"],
}
```

To be honest about what a listing means: a package with the keyword is listed as npm has it,
unreviewed. An entry in `data/hanko.ts` is looked over lightly before it goes in (it is
published, it does what the line says), and that is all. Neither is maintained, audited or
supported by inkan. Issues and releases stay with their authors, and a package that misuses
the keyword, or no longer works with a current inkan, may be left off the list.
